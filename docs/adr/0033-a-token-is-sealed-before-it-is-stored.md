# 0033 — A token is sealed before it is stored

- Status: accepted
- Date: 2026-09-22

## Context

ADR 0026 built the QuickBooks adapter and left one thing deliberately
unbuilt: `QboTokenStore` is a port — `load(realmId)` / `save(realmId, tokens)`
— whose only implementation is `InMemoryQboTokenStore` under
`@recouple/qbo/testing`, placed there so no production path can reach it. ADR
0031 then built the scheduler on top of that gap and named it in §7: the sync
runs end to end, every day, and records `not_configured` for every connection,
because `qboTokenStoreFromEnv` returns `undefined`.

So the whole ERP discovery path — the ~70% of deductions a supplier never
surfaces, which is the coverage thesis (STRATEGY §5) — is a scheduler that is
proven to run and a vendor that is not wired. This ADR wires it, and nothing
else: no OAuth consent flow, no UI, no write to QuickBooks.

Five constraints decide the shape, and they are constraints rather than
preferences.

**Credentials do not go in an application table.** CLAUDE.md puts portal and
ERP credentials in KMS-backed storage. Intuit makes the rule bite harder than
usual: refresh tokens are replaced on every refresh and the old one dies the
instant the new one is issued, so a plaintext row anybody can `select *` is a
live credential leaked, and a row anybody can `update` is a customer's
connection stranded with no repair but going back for consent.

**`pnpm db:test` runs on vanilla Postgres 16.** `scripts/db-test.sh` applies
every migration to a scratch database created by `initdb` — no Supabase, no
`supabase_vault`, no `pgsodium`, no `pg_tle`. A migration that needs one of
those cannot be applied by the suite that proves our invariants, and an
invariant nothing reads back is prose (ADR 0003 made exactly this trade when it
refused pgTAP).

**The tests run with no cloud.** Nothing in this repository opens a socket to a
vendor in CI. ADR 0026 injects `fetch` for that reason; a token store that can
only be exercised against a live KMS is a token store nobody will exercise.

**No plaintext token anywhere but in memory, briefly.** Not in a column, not in
a log line, not in an event payload — the queue is a third party and the payload
is durable there (ADR 0021) — not in an error message, and not in a fixture
committed to git.

**The service role is never used, and the decryption key never touches the
database.** Invariant 6 is one line about the first. The second is the point of
doing this at all: a database compromise that hands over every row must not hand
over a customer's ledger with it.

## Decision

### 1. Envelope encryption with a cloud KMS, ciphertext at rest in Postgres

Three options were live, and the constraints above choose between them rather
than taste doing it.

**(a) Supabase Vault.** The obvious answer for a Supabase deployment: secrets
encrypted at rest with a key held outside the database, `vault.create_secret()`
and `vault.decrypted_secrets` as the interface. It is refused on the second
constraint. Vault is `supabase_vault`, which rests on `pgsodium`, and neither
exists on the vanilla Postgres 16 that `pnpm db:test` runs against — so the
table could not be created by a migration the suite applies, and
`supabase/tests/` could not read the end state back. Working around that means
an `if exists` branch in a migration, one schema in CI and a different one in
production, and the invariant suite proving the wrong one. Vault also puts the
decryption path *inside* the database: a role that can read a view can read the
secret, which is the property we are specifically trying not to have. Refused
for environment parity first and for that second.

**(b) Envelope encryption with a cloud KMS, ciphertext at rest in Postgres.**
A data key per token set, generated by AWS KMS (`GenerateDataKey`), used once
locally under AES-256-GCM, and stored beside the ciphertext in its wrapped form.
Decryption is `kms:Decrypt` on the wrapped key, in the application, with
credentials the database does not have. The database holds ciphertext and a key
id and can be dumped without disclosing anything. It needs no extension, so the
table is an ordinary table a migration creates and suite 21 reads back on
vanilla Postgres. And the cipher is a port with two implementations, so the
tests exercise the real code path with no cloud (§4). **Chosen.**

**(c) An external secrets manager** (AWS Secrets Manager, Vault, Doppler). The
strongest isolation: the token never enters our database in any form. It is
refused on operational shape rather than on security. A rotation here is not a
rare operator event — it happens on *every* refresh, roughly hourly per
connection, and ADR 0026 requires it to be durable before the next API call.
That makes a per-tenant secret a per-tenant secret being rewritten hourly, in a
product whose whole tenancy story is `org_id` plus RLS: we would be maintaining
a second, parallel authorization model in a vendor's IAM for every customer we
onboard, with none of the append-only history the post-audit defence is built
on, and with a second failure domain in the path of a scheduled job. Secrets
Manager also bills per secret per month and per API call, which prices a
per-connection secret rotated hourly badly. Rejected, and worth revisiting only
if the ciphertext-at-rest posture is ever ruled insufficient — the
`TokenCipher` port is where that change would land.

### 2. `accounting_credentials`: append-only, and a rotation is a new row

Migration 0025 adds `accounting_credentials`: `org_id`, `connection_id`, the
`ciphertext`, the `wrapped_key`, the `key_id`, the `cipher` name,
`access_expires_at`, `refresh_expires_at`, `created_by`, `created_at`, and a
`seq` identity column. The current tokens are **the latest row for the
connection**, and there is no other kind of row.

Append-only on migration 0004's pattern exactly — revoke UPDATE/DELETE/TRUNCATE
from `app_rw` and `app_ro`, INSERT and SELECT to `app_rw`, SELECT to `app_ro`,
plus `no_update_delete` and `no_truncate` on `app.block_mutations()`, because a
grant answers for `app_rw` and the trigger is what answers for the owner.

This is not append-only by habit. It is append-only because of what an UPDATE
here would be: the one statement that can destroy a customer's connection
irrecoverably. A crash midway through `update … set ciphertext = …` leaves
either the old token — which Intuit has already killed — or a half-written row,
and both mean consent again. An INSERT cannot do that: the previous row is
still there, still decryptable, and the failure mode of a partial write is a row
that was never committed. The history of rotations is the audit trail for free,
and a connection whose rows stop appearing hourly is visibly stuck.

`seq` exists because "latest" has to be unambiguous. `created_at` defaults to
`now()`, which is fixed for a transaction, so two rows written in one
transaction would tie and the ordering would be whatever the planner felt like.
`seq` is `generated always as identity`, so the order rows were written in is
the order they are read back in.

**No plaintext column of any kind, and the suite asserts it against the
catalogue.** Suite 21 reads `information_schema.columns` and asserts set
equality against the twelve columns this migration creates, in both directions,
the way `packages/store-postgres/test/doc-types.test.ts` asserts `DOC_TYPES`
against `pg_constraint`. A later migration that adds `refresh_token` fails there
on the day it is written rather than in review. The two `*_expires_at` columns
are timestamps, not credentials: they are in the clear so an operator can see
which connections are about to strand without anybody decrypting anything.

The tenancy tie is a composite foreign key, `(org_id, connection_id)` against
`accounting_connections (org_id, id)`, which ADR 0025 §7 introduced for
`deduction_identifiers` — declarative, always enforced, and it does not care
which role is writing. It needs `unique (org_id, id)` on
`accounting_connections`, which is implied by the primary key and costs one
index. A ciphertext this tenant can read, hung off another tenant's connection,
would otherwise be a token set decrypted under the wrong encryption context and
refused — but refused at the vendor, after a `kms:Decrypt` call, rather than by
the database. The database is the referee.

RLS like every table: `tenant_read` on the org claim, `tenant_insert` on the org
claim *and* `app.member_may_write()`, and update/delete policies present so a
grant issued in a hurry lands on a rule rather than on nothing — the grant
itself is revoked.

### 3. The `TokenCipher` port: encrypt, decrypt, and an encryption context

`@recouple/crypto` is a new package holding one port:

```
encrypt(plaintext, { orgId, realmId }) → { cipher, keyId, wrappedKey, ciphertext }
decrypt(sealed,    { orgId, realmId }) → plaintext
```

A new package rather than a file in `store-postgres` for two reasons. ADR 0026
says `packages/qbo` never reads `process.env`, and it is worth that rule still
being true of the thing that reads `QBO_TOKEN_KMS_KEY_ID` — so the cipher lives
outside both. And `LocalTokenCipher` needs a `testing` entry point that the
package index does not re-export (§4), which `store-postgres` does not have and
should not grow.

**The encryption context is `{orgId, realmId}`, and it is authenticated at both
layers.** KMS binds it to the wrapped key, so `kms:Decrypt` fails outright if
the context differs; and the same canonical string is the AES-GCM additional
authenticated data, so the local half fails too. Two consequences worth stating.
A ciphertext lifted out of one tenant's row and inserted into another's does not
decrypt — a row-level compromise of the database is not a cross-tenant
credential leak. And a ciphertext replayed against another *company* of the same
tenant does not decrypt either, so the realm check in §5 has a cryptographic
backstop rather than being the only guard.

A tampered ciphertext is refused by GCM's tag, not detected later by something
noticing the JSON is malformed. That is why AES-GCM and not AES-CBC.

`KmsTokenCipher` is the production implementation: `@aws-sdk/client-kms`,
`GenerateDataKey` with `KeySpec: AES_256` for a write and `Decrypt` for a read,
one KMS call per operation. Credentials come from the environment the standard
SDK way — the provider chain, so a Vercel deployment uses
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` and a future EC2 or Lambda host uses
its instance role without a code change. The only variable this repository reads
by name is `QBO_TOKEN_KMS_KEY_ID`. The plaintext data key is zeroed after use;
that is hygiene rather than a guarantee, because V8 copies buffers, and it is
written down as hygiene.

**A decryption failure is a typed error carrying ids.** `TokenDecryptionError`
names the cipher, the key id and the connection — never the ciphertext, never
the wrapped key, never what the plaintext would have been. An error from the SDK
is caught and replaced by its class name for ADR 0031 §2's reason: a message off
this path travels into logs, run histories and third-party retention.

### 4. `LocalTokenCipher` is under a `testing` entry point, and cannot be reached from production

The precedent is exact and there are three of them: `NullScanner`,
`InMemoryQboTokenStore` and `@recouple/pipeline/testing`. A fixture reachable
from a production path is a fixture that will eventually run there, and this one
would run there holding a customer's QuickBooks credentials.

So `LocalTokenCipher` ships from `@recouple/crypto/testing`, the package index
does not re-export it, and `packages/crypto/test/cipher.test.ts` asserts that by
importing the index and checking the export is absent — the assertion
`packages/adapters/test/accounting.test.ts` already makes about
`InMemoryAccountingSource`. Nothing in `apps/web`, `packages/store-postgres` or
`scripts/` imports the `testing` entry, and `qboTokenStoreFromEnv` has no branch
that could select it: there is one cipher constructor in the production path and
it is `KmsTokenCipher`.

`LocalTokenCipher` does envelope encryption for real — a random data key per
operation, wrapped under a root key with the same encryption context as AAD —
rather than being a stub that returns its input. Which means the round trip, the
tamper refusal and the wrong-context refusal are the same code paths in both
implementations, and a test that passes with the local cipher is evidence about
the real one. The root key is random per instance unless one is supplied, so a
`LocalTokenCipher` that somehow did run in production would lose every token on
restart rather than protect them with a key in the source.

### 5. `PostgresQboTokenStore` is scoped to one connection

It implements `QboTokenStore` and runs as `app_rw` with the tenant's claims set
transaction-locally, through the same `withTenant` shape as `workflow.ts`,
`discovery.ts` and `connections.ts`. The service role appears nowhere.

It is constructed with `{orgId, userId}`, a `connectionId`, a `realmId` and a
cipher — **one store per connection**, not one store with a realm-keyed map.
The port's `load(realmId)` / `save(realmId, …)` signature invites the second
reading, and it is the wrong one here: a store that resolves a realm to a
connection at call time is a store that can be asked for a realm it was not
built for, and the answer would depend on a lookup rather than on the claims the
transaction is running under. So the realm is fixed at construction from the
connection row the job already read under RLS, and a `load` or `save` naming a
different one raises `QboRealmMismatchError` — named, with both realms and the
connection id, none of which is a credential (migration 0024 says so of
`provider_account_id` in as many words).

`load` selects the latest row for the connection — RLS scopes it to the org —
and decrypts. No row is `undefined`, which is what `QboClient` turns into
`QboAuthError` ("the connection has not been authorised"), not into an empty
ledger. `save` encrypts and inserts, and the insert is what makes the rotation
durable before the adapter uses it (ADR 0026 step 2 before step 3). The
adapter's ordering is unchanged and untouched; what changes is that `save` now
means something.

### 6. `qboTokenStoreFromEnv` fails closed, per `scannerFromEnv`

`QBO_TOKEN_KMS_KEY_ID` is the one variable, and absent it there is no cipher, so
there is no store, so `accountingSourceFromEnv` answers `not_configured` with a
reason naming the variable — the path ADR 0031 §7 built and this ADR reaches
rather than replaces. No key id builds nothing; it does not build a cipher that
throws on first use, and it does not fall back to anything. `scannerFromEnv`'s
rule, for `scannerFromEnv`'s reason: a `NullScanner` reports an error rather
than a clean bill of health, and an unconfigured deployment must not be able to
read a stranger's ledger at all.

The store is built per connection inside `resolve(connection)`, from the
identity the sync is already acting as and the `providerAccountId` on the
connection row. That is why the factory now takes the identity: a token store
with no claims is a token store with no tenant, and there is no such thing here.

### 7. `pnpm link:qbo` is how the first tokens get in

There is no OAuth consent flow yet (ADR 0031 said so and this ADR does not
change it), so the first token set is placed by an operator, from a `.env`,
exactly the way `pnpm link:retailer` places a debtor alias and
`pnpm link:provenance` places an arrival.

`scripts/link-qbo.ts` takes explicit `--org` and `--as` with no defaults,
resolves both against the database, refuses a member who may not write in that
org, creates the `accounting_connections` row if it is absent, and saves the
tokens through `PostgresQboTokenStore` with the **real** `KmsTokenCipher`.
There is no flag that selects the local one. It prints ids and never a token,
not even a prefix of one, and `--dry-run` says what it would do without calling
KMS or writing a row.

`docs/qbo-credentials.md` is the once-per-deployment AWS setup, written for
somebody who does not work in AWS every day: one key, one IAM identity with
`kms:Encrypt`, `kms:Decrypt` and `kms:GenerateDataKey` scoped to that key alone,
and the four environment variables on Vercel and in the laptop `.env`.

## Consequences

- The ledger sync can be configured. A deployment with a KMS key and an Intuit
  app reads a customer's ledger; one without records `not_configured` exactly as
  before. Nothing about the scheduler, the run log or the coverage view changes.
- The repository now depends on AWS for one thing, and it is a narrow thing: two
  API calls, one key, and an IAM identity that can do nothing else. Every test
  runs without it.
- A customer's tokens survive in the database as a chain of ciphertexts, one per
  rotation, none of which can be read without a KMS call nothing in the database
  can make. A database dump is not a credential. The cost is storage — one row
  per connection per hour, a few hundred bytes — and that is worth the failure
  mode it removes.
- Rotating the KMS key itself is not automatic. `key_id` is on every row, so a
  re-encryption pass is possible and a row encrypted under the old key still
  decrypts while the old key is enabled. There is no script for it and this ADR
  does not pretend otherwise: a key rotation is a task, and the column is what
  makes it a tractable one.
- The first token set is placed by hand. Until a consent flow exists, connecting
  a customer means an operator running a command with their refresh token in a
  `.env` — which is a real exposure, in a file on a laptop, and the reason the
  doc says to delete the line afterwards. A consent flow is the fix and it is
  not this change.
- `store-postgres` now depends on `@recouple/qbo` and `@recouple/crypto`. No
  cycle: neither depends on it.

## Invariants touched

- **1 (no submission without an approval).** Untouched. Nothing here inserts a
  `submissions`, `writebacks` or `writeoffs` row, and no gate function is read,
  replaced or referenced.
- **2 (append-only).** Extended by one table. `accounting_credentials` joins the
  set on migration 0004's pattern and this migration names it, per invariant 2's
  rule that the list lives in the migrations rather than in prose.
  `supabase/tests/21_a_token_is_sealed.sql` reads the end state back. No
  existing append-only table gains an UPDATE or DELETE grant, and
  `accounting_connections` — which is deliberately outside the set (ADR 0031 §1)
  — gains only a unique constraint.
- **3 (money is integer cents).** Not engaged. No money column, no arithmetic,
  no amount crosses this path.
- **4 (document content is untrusted).** Held. No model is constructed here,
  with or without tools. What this change is careful about is the mirror image
  of invariant 4's concern: nothing carries a *secret* outward, the way nothing
  there carries untrusted text inward. Errors carry class names and ids; the
  event payload is unchanged; the run row is unchanged.
- **5 (Jev behind `DecisionProvider`).** Not engaged.
- **6 (RLS everywhere; the service role never in a request path).** Held, and
  worked for. The new table has RLS with per-command policies. Every read and
  write is `app_rw` with the tenant's claims set transaction-locally. No
  `security definer` function is added — unlike ADR 0031, this path has no
  refusal that must record itself, so there is nothing to escape a policy for.
  The service-role key appears nowhere in this change, and neither does any AWS
  credential in `packages/qbo`.
- **7 (thresholds auto-tighten only).** Not engaged. No threshold is added and
  no guarded column changes.

## Rollback

Drop `accounting_credentials` and the `accounting_connections_org_id_id_key`
constraint in a new migration — never by editing 0025. Delete
`packages/crypto`, `packages/store-postgres/src/credentials.ts`,
`scripts/link-qbo.ts`, `docs/qbo-credentials.md`, their tests, the export line
in `store-postgres`'s index and the `link:qbo` script entry, and return
`qboTokenStoreFromEnv` to `undefined`. The scheduler then records
`not_configured` again, which is where ADR 0031 left it: a working seam with
nothing in it.

Unsetting `QBO_TOKEN_KMS_KEY_ID` is the same rollback without a deploy, and it
is the one to reach for first. Deleting the KMS key is not a rollback — it makes
every stored ciphertext permanently unreadable, and the repair is asking every
customer for consent again. Disable the key instead, and disable the connections
before that.
