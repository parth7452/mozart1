# 0014 — A document's bytes live in Postgres, for now

- Status: accepted
- Date: 2026-09-18

## Context

`BlobStore` had exactly one implementation, `InMemoryBlobStore`, and
`PostgresStore` used it by default. So every document Phase 1 ingested existed
only for the life of the Node process: the `documents` row outlived it, carrying
a `storage_ref` that nothing could resolve.

That is not a missing feature, it is a case whose evidence cannot be produced —
and producing the evidence is the entire job of a deductions packet. It was also
invisible to the tests, because a test that writes and reads in one process never
notices that the bytes were never anywhere.

Three options:

1. **Supabase Storage with the service-role key.** Simple, and it puts the
   service-role key in a request path. That is invariant 6, and it is the one
   invariant the database cannot enforce for us.
2. **Supabase Storage with the user's own JWT and storage RLS policies.** No
   service role, but it means a second authorization story — storage policies —
   kept in step by hand with the table policies that already exist. Two models
   that must agree are two models that will eventually disagree.
3. **Bytes in Postgres, in a table under the same RLS as everything else.**

## Decision

Option 3, behind the existing `BlobStore` port. `document_blobs` holds the bytes,
with RLS on, one policy per command, a writer role required to write, and the
append-only triggers — the same shape as every other table here. A blob is
readable exactly when the document row that points at it is readable, because it
is the same policy doing the deciding.

`PostgresBlobStore` is now the default, not an opt-in: an in-memory blob store is
something a test may choose, never what a caller gets for not choosing.

Two details that are decisions rather than details:

- **The document id is generated by the application, not by the insert.** The
  bytes are keyed by it and are written first, so a `documents` row never exists
  without the bytes it points at.
- **`document_blobs` has no foreign key to `documents`.** It cannot, given the
  write order above. The asymmetry is deliberate: bytes nothing references are
  garbage and can be collected, while a document row whose bytes are missing is
  a lie the rest of the system will believe.

## Consequences

A deduction notice is tens to hundreds of kilobytes and a case has a handful of
documents, so this is comfortable for a long time. It will stop being
comfortable — large scanned PDFs, a big corpus, backups that carry every byte of
every document. The port is the plan: moving to object storage means a second
`BlobStore`, and the authorization story to solve first is option 2's, not this
one's.

`pg`'s bytea round-trip buffers the whole document in memory. Streaming a large
file to a browser will want a signed URL from real object storage rather than
this table.

## Invariants touched

**4**, supported rather than changed: the scan gate says no document is read
before it is scanned clean, and a document whose bytes have evaporated cannot be
re-read at all.

**6**, kept: no service-role key appears in a request path, which options 1 and
2 both pressed against.

## Rollback

Reverting means documents that exist only in memory again. The table can stay
even after object storage arrives; it is the fallback that needs no bucket.
